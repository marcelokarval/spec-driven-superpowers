# Task 0002: Create proposals and previews

## Outcome

Let the AI submit a status-filter proposal and let the operator inspect a faithful preview without changing the saved view.

## Inputs

Read the project rules and `README.md`, plus proposal, design, capability spec, and Task 0001's integrated persistence contract.

## Acceptance

- A proposal records an operation ID, view ID, expected version and canonical proposed filter content.
- Creating or previewing a proposal leaves the view filters and version unchanged and does not create permission.
- Preview displays current versus proposed filters, the expected version and the affected synthetic orders.
- Reusing an operation ID with identical canonical content returns the existing proposal/result; different content or operation type returns an identifier conflict without changing the view.
- Unsupported filter fields are rejected before recording.

## Verification

Use TDD and run `node --test tests/app.test.mjs`. Cover immutability, preview contents, status filter validity, canonical equality and ID conflict behavior.

## Definition of done

Return scoped code and tests bound to one revision. Coordinator verifies the proposal remains inert and that UI offers no apply side effect from proposal creation or preview.

## TDD

RED: add scenario tests including ID replay/conflict and view immutability. GREEN: implement canonical payload comparison and proposal/preview UI. REFACTOR: centralize validation and stable serialization.

## Boundaries and delivery

Write only `src/app.js`, `index.html`, `src/styles.css` and `tests/app.test.mjs`. No provider, remote call or team-access policy is in scope.
