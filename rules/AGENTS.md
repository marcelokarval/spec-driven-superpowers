# Opt-in ASDS project profile

This template applies only to the project/tree where its owner explicitly adopts
it. It is not a machine-wide directive. Preserve higher-priority instructions and
the user's approval boundaries.

- Global skill availability does not activate engineering workflows for ordinary
  questions. For suitable ASDS work, inspect the intended project's OpenSpec state
  and ask before creating a missing `openspec/`, unless already explicitly authorized.
  Reuse existing configuration; refusal continues without OpenSpec artifacts.
- OpenSpec governs requirements; adapted Superpowers practices guide understanding,
  task writing and planning review. ASDS itself does not implement future tasks.
- For accepted planning, use `planning-manifest.json`, `tasks.md` and linked task
  microcontracts. Only the planning coordinator updates this package before delivery.
- Resolve and inspect an existing package before reviewer preflight. If a reuse handoff
  lacks lineage/locator, bounded read-only discovery may select only one direct child of
  `openspec/changes`; zero or multiple matches require an exact locator. Missing lineage
  never authorizes a write, and reviewer unavailability does not block read-only inspection.
- A new delivery starts with future-work checkboxes open. After handoff, `tasks.md`
  checkbox state is consumer progress; the progress-normalized manifest/hash is not
  a second ledger. Never reopen `[x]` without the consumer reopen protocol and matching
  receipt/journal evidence or another concrete contradiction.
- Discover actual project verification commands as future contract data; do not run
  project implementation merely to deliver planning.
- Recommend parallelism from dependencies, paths and resources without spawning workers.
- Bind fidelity, quality and readback evidence to the planning revision. Disclose
  self-review and missing independence; do not claim delivered without readback.
- A coherent already-delivered package with no material plan change keeps its review;
  only a materially new candidate reaches the fresh-review availability gate.
- Preserve useful visual evidence according to project storage/privacy policy.
- A cancelled tool return is not evidence. Preserve the last coherent planning
  revision and report incomplete persistence/review without false delivery.
- If proven corruption is restored byte-for-byte to the delivered candidate,
  references, manifest and reviews, report `restored existing delivered state` and
  preserve the prior review. Material change creates a new candidate and fresh review.
- Never claim a write, validation, readback, database record, signature or review
  without direct evidence for that exact operation.
- Do not commit, push, archive, publish, install globally or modify credentials,
  provider settings or permissions without explicit authorization.

Project owners should add their test commands, concurrency budget, evidence
location and review/approval requirements before adopting this template.
