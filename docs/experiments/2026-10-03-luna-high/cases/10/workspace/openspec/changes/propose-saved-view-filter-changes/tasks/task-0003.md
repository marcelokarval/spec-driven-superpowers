# Task 0003: Apply with current permission and version

## Outcome

Add a separate explicit local permission action and a safe, idempotent apply operation for an existing proposal.

## Inputs

Read project rules and the proposal, design, capability spec, and integrated contracts from Tasks 0001 and 0002.

## Acceptance

- The operator must explicitly grant a synthetic permission scoped to the operation ID, view ID and expected version, with expiry and revocation/consumption state.
- Apply rejects missing, expired, revoked, consumed, or differently scoped permission and rejects an outdated expected version.
- On success, one IndexedDB transaction updates filters/version, consumes permission, and records the result.
- An identical retry returns the previous result without incrementing the version again; conflicting content for that ID fails.
- Rejection or transaction failure leaves no partial view, permission or result mutation.

## Verification

Use TDD and run `node --test tests/app.test.mjs`. Test each permission-invalidity state, stale version, successful one-time apply, exact replay, conflicting ID and rollback on failed transaction.

## Definition of done

Return scoped code and tests bound to one revision. Coordinator checks all failure paths preserve state and the UI has distinct propose, preview, grant and apply actions.

## TDD

RED: add tests for every guard, exact replay and atomic failure. GREEN: implement permission validation and apply in the transaction boundary. REFACTOR: make authorization and version checks explicit and reviewable.

## Boundaries and delivery

Write only `src/app.js`, `index.html`, `src/styles.css` and `tests/app.test.mjs`. Synthetic permission is not an authentication or production authorization claim. Team access policy remains out of scope.
